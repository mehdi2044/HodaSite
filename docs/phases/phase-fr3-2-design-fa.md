# FR3.2 — طرح فنی آزمایش نمای واقعی

این سند طرح آزمایش است. انتخاب تأمین‌کننده، اعتبارسنجی کیفیت و بودجه هنوز باز است.

| موضوع | FASHN Try-On Max | Amazon Nova Canvas |
| --- | --- | --- |
| قرارداد آزمایش | عکس شخص و عکس یک محصول به `tryon-max`، دریافت شناسهٔ پردازش و بررسی وضعیت. پوشاک و چند نوع اکسسوری در مستندات ذکر شده‌اند. | فراخوانی Bedrock با `VIRTUAL_TRY_ON`، تصویر مبنا، تصویر مرجع محصول و ماسک مناسب. ماسک صریح برای آزمون حفظ پس‌زمینه و بخش‌های خارج از لباس. |
| ترکیب چندتکه | صحت ترکیب چندتکه و حفظ تکه‌های قبلی باید آزمایش شود. | درج مرحله‌ای می‌تواند کیفیت چهره یا لبه‌ها را تغییر دهد. ترتیب و ماسک هر مرحله باید جدا بررسی شود. |
| نگه‌داری داده | Base64 برای ورودی خصوصی و خروجی؛ بازهٔ نگه‌داری خروجی Base64 طبق مستندات کوتاه‌تر است. metadata درخواست جدا می‌ماند. | ورودی در حافظه و فراخوانی در Region مصوب. تنظیمات retention، logging و قرارداد مدل/Region پیش از ارسال داده راستی‌آزمایی شود. |

منابع رسمی: [Try-On Max](https://docs.fashn.ai/api-reference/tryon-max)، [حریم خصوصی FASHN](https://docs.fashn.ai/api-overview/data-retention-privacy)، [راهنمای Virtual Try-On در Nova Canvas](https://docs.aws.amazon.com/nova/latest/userguide/image-gen-vto.html).

آزمایش بعد از تصویب بودجه با عکس ساختگی یا نمونهٔ دارای مجوز انجام می‌شود. مجموعهٔ ثابت شامل بالاتنه، شلوار، لباس یک‌تکه، کیف، شال و کلاه، تصاویر با رنگ نزدیک و متضاد و ترکیب‌های ۲ تا ۴ تکه است. هر دو سرویس روی ورودی، ترتیب و سقف خروجی قابل مقایسه سنجیده شوند. دو ارزیاب حفظ چهره و ژست، رنگ و بافت، لبه و پوشاندن، و تغییر ناخواسته را امتیاز دهند. زمان p50/p95، هزینهٔ هر خروجی پذیرفته‌شده، خطا، خروجی بی‌کیفیت و هزینهٔ retry ثبت شوند. آزمایش آفلاین از پاسخ‌های ساختگی فقط برای درستی سامانه استفاده می‌کند.

کلید cache با HMAC سمت سرور از قلمرو کاربر و بازار، revision تصویر و رضایت، شناسهٔ مدل/نسخهٔ provider، ترتیب پوشش، revision و hash هر Cutout، گزینه‌های خروجی و نسخهٔ pipeline ساخته می‌شود. cache خروجی خصوصی داخل قلمرو همان مالک است. فقط نمونه‌های عمومی مجاز می‌توانند cache مشترک جداگانه داشته باشند. انقضا، حذف و لغو رضایت cache و object متناظر را باطل می‌کند. کنترل مالکیت روی هر خواندن، URL امضاشدهٔ کوتاه، حذف EXIF، محدودیت حجم/نوع و رمزنگاری ذخیره‌سازی لازم است. عکس، base64 و URL امضاشده در log و trace ثبت نشوند. پاک‌سازی object و metadata داخل سیاست retention، export و حذف حساب آزمایش شود.

درخواست کلید idempotency مالک‌محور و payload hash دارد. DB با قید یکتایی جلوی dispatch دوباره را می‌گیرد. تکرار همان درخواست نتیجه/وضعیت موجود را می‌دهد و reuse کلید برای payload متفاوت خطاست. موجودی سکه و سقف بودجه در تراکنش با lock کیف و ثبت intent پایدار بررسی می‌شوند. cache hit طبق سیاست مصوب بدون reserve جدید است. worker پس از commit ارسال می‌کند. موفقیت قطعی settle می‌شود و شکست قطعی release/refund idempotent دارد. نتیجهٔ نامعلوم نیازمند reconciliation است. timeout پس از ارسال اجازهٔ ارسال دوباره یا refund قطعی را به‌تنهایی نمی‌دهد. تست هم‌زمانی شامل دوبارکلیک، retry پس از crash، dispatch نامعلوم و موفقیت دیررس است.

پنل مدیریت با مجوز سرور، audit و پیش‌فرض خاموش، provider/model/region، سقف روزانه، هزینهٔ سکه، محدودیت خروجی، retention، kill switch و وضعیت اتصال را کنترل می‌کند. secret در محیط سرور می‌ماند. API این مرحله صرفاً پس از تصویب provider و بودجه در مسیر جداگانهٔ دارای ADR اجرا خواهد شد.

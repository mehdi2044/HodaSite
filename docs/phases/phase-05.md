# Phase 05 — Shipping Workflows, Tracking, Invoice PDF, Full RBAC & Audit, Backup UI, System Health

## Goal
Operations are complete: multi-leg shipping per market, customer tracking, invoices, full permission model with scopes and MFA, immutable audit, and the owner's backup/restore control panel.

## Scope
1. **Shipping workflows**: admin Settings → Shipping: per market define workflow(s) with ordered leg templates (type INTERNATIONAL/DOMESTIC, label I18n, default carrier name, tracking URL template like `https://…/{tracking}`), default workflow per market. Seed: TR = [Domestic]; IR = [International, Domestic]; CA = [International, Domestic] with a second optional "Door-to-door" single-leg workflow.
2. **Shipments**: on PAID (or manually) create `Shipment` from the market's default workflow; admin order page gets a Shipping panel: per leg set carrier, service, tracking no., cost + currency, status, shipped/ETA/delivered dates; add/remove legs ad hoc; partial shipments (subset of items) supported in data + UI (simple). Status roll-up: order becomes SHIPPED when first leg ships, DELIVERED when last leg delivered. `TrackingEvent` manual entries; `CarrierProvider` interface + `manual` implementation (future: PTT/Aras/Yurtiçi/Canada Post adapters).
3. **Customer tracking**: order page timeline with legs, tracking links, ETA; public tracking page by order number + email (no login). Emails `order.shipped` (per leg optional) and `order.delivered`.
4. **Invoice PDF**: generated on PAID (job), trilingual template (customer's locale; Persian with Jalali date and Persian digits; RTL layout), brand from settings, breakdown lines, bank/payment info, tax id fields per market (labels only; statutory compliance out of scope), stored as private Media, downloadable by customer/admin, regeneration button. Use `@react-pdf/renderer` or Puppeteer-less HTML→PDF (`playwright` chromium in container acceptable) — pick one and document.
5. **Returns & size/color exchange (D33)** on the Phase 04 data model: customer requests return or exchange from a delivered order (reason code, items, photos optional, desired variant for exchange); admin queue with statuses; on RECEIVED: `StockMovement(RETURN)` with condition RESTOCK/QUARANTINE/DAMAGED (only RESTOCK increases sellable stock); exchange creates a linked `Order(kind=EXCHANGE, parentOrderId)` with zero-payment when same price or a difference payment/credit; refund to original method (manual record) or `StoreCredit` usable at checkout. Eligibility rules (days per market, categories) simple config now; full portal/analytics in Phase 09.
6. **RBAC full** per D-spec §9: permission namespace (appendix B), Roles editor (matrix UI), user role assignment with scope (markets, categories, sections), per-user overrides, MFA enforcement for `owner`/`admin` roles (TOTP with QR, backup codes), session list & revoke, "view as role" preview. Every admin server action and admin API route goes through `assertCan()`; scope filtering applied in queries (e.g., TR manager sees only TR orders).
   **Permission test matrix (V-4, blocking):** a generated test suite over the cartesian product **Subject × Action × Scope** — every seeded role (+ one user with an override, + an unauthenticated session) × every permission in the namespace × in-scope / out-of-scope resource. Each case is asserted **twice**: once through the UI/server action and once by calling the endpoint or server action **directly** with a forged payload (bypassing the UI), because a hidden button is not authorization. Expected-deny cases must return 403/throw, never 200 with filtered data, and must not leak existence (404 vs 403 policy documented). Any permission added later without a matrix row fails CI.
7. **Audit log**: append-only; viewer with filters (user, entity, action, date), diff view; sensitive fields (cost, bank accounts, permissions, FX manual, settings, refunds) all logged. DB rule: no UPDATE/DELETE on `AuditLog` (Postgres rule/trigger).
8. **Backup & Restore** per `04_DATABASE_AND_BACKUP.md` §3.3–3.6 (D23/D36): `ops` container in compose (postgres-client, mc, zstd, docker CLI access limited to `exec app`), hardened `restore.sh` (zip validation, safety backup, mandatory maintenance handshake, atomic media swap, trap cleanup, verify), `verify.sh` full checks; admin: list, backup now, download, upload (quarantine → validate), **RestoreRequest** flow (owner + password + TOTP → `ops` executes → live log), weekly verify results, settings (time, retention, include media; off-site status only — credentials in env). Off-site missing → red alert.
9. **System Health** page: DB size, media size, disk free, last backup age & verification, off-site sync status, FX ages, job queue backlog/failures, email provider status, app version/migration, error count (last 24h). `SystemAlert` table drives topbar badge (FX stale, backup failed, low stock, unpaid backlog).
10. **Market on/off** + **announcement bar** already exist; add "sales paused" mode per market (browse but no checkout) with message.

## Acceptance criteria
- IR order: leg 1 tracking visible to customer; leg 2 added; delivered → order DELIVERED; TR order has no international leg.
- Invoice PDF renders correctly in fa (RTL, Jalali), tr, en; opens in mobile browsers.
- Warehouse role cannot edit price via UI or direct server action; TR-scoped admin cannot fetch IR order by id (403).
- Owner login enforces TOTP; backup codes work.
- Backup now → download → delete a product → upload same file → request restore → `ops` restores → product back; safety backup exists; maintenance mode toggled automatically; restore refused without MFA; a crafted zip with `../` entries is rejected; killing the process mid-media-restore leaves the previous media intact.
- Exchange M→L: linked order created, stock of M returned (RESTOCK) and L consumed; margin/finance hooks left for Phase 06.
- AuditLog row cannot be updated/deleted even by superuser SQL role used by app.

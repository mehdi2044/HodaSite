# راهنمای نصب و راه‌اندازی (برای مهدی — بدون نیاز به برنامه‌نویسی)

این راهنما در چهار بخش است:
A) مخزن و چرخهٔ توسعه، B) اجرا روی لپ‌تاپ، C) اجرا روی سرور، D) کارهای روزمره (بکاپ، به‌روزرسانی).
عامل اجرایی موظف است هر وقت مرحله‌ای عوض شد، همین فایل را به‌روز کند.

---

## A) مخزن موجود و چرخهٔ توسعه

### A1. شروع از نسخهٔ فعلی

مخزن پروژه از قبل ساخته شده است. برای ادامهٔ کار از نسخهٔ فعلی `main` در `mehdi2044/HodaSite` استفاده کنید؛ بستهٔ اولیه را دوباره روی مخزن آپلود نکنید. روش دریافت کد در بخش B آمده است. سند مادر کامل و اعتبارنامه‌ها خارج از مخزن عمومی می‌مانند.

### A2. عامل اجرایی

عامل اجرایی از `AGENTS.md` و جدول «وضعیت معتبر امروز» در `docs/02_DECISIONS.md` شروع می‌کند. پرامپت هر فاز در `docs/prompts/` است. انتخاب ابزار، الزام به همکاری یا تأیید پیکسل ایجاد نمی‌کند.

### A3. چرخهٔ هر فاز

1. شرح فاز و تصمیم‌های جاری خوانده می‌شود؛ تغییر روی شاخهٔ جدا انجام می‌شود.
2. عامل اجرایی پیاده‌سازی، بررسی کیفیت و شواهد آزمون را در PR ثبت می‌کند.
3. پس از سبزشدن `checks` / `docker` / `docker-runtime` روی آخرین head و رفع اشکال‌های مسدودکننده، همان عامل می‌تواند PR را مرج کند؛ اجازهٔ موردی شما یا تأیید پیکسل لازم نیست (D50/D63).
4. نتیجهٔ مرج و محدودیت‌های باقی‌مانده گزارش می‌شود. آزمون واقعی گوشی و staging طبق D51 همچنان باید انجام شود؛ این آزمون با مجوز مرج فرق دارد.

### A4. محافظت از main

مخزن public است (D45). همهٔ تغییرها، حتی اسناد، از شاخه + PR عبور می‌کنند. push مستقیم به main، force-push، دورزدن حفاظت شاخه و مرج با CI قرمز/ناقص مجاز نیست. قواعد قدیمی «مرج فقط توسط مالک» و «دو بازبین اجباری» جایگزین شده‌اند.

## B) اجرا روی لپ‌تاپ (برای دیدن سایت قبل از سرور)

### B1. نصب ابزارها (یک‌بار)

1. **Docker Desktop**: از docker.com دانلود و نصب کنید. بعد از نصب باید در نوار وضعیت آیکون نهنگ سبز باشد.
2. **Git**: از git-scm.com (ویندوز) نصب کنید؛ روی مک از قبل هست.
3. (اختیاری) **VS Code** برای دیدن فایل‌ها.

### B2. گرفتن کد

در Terminal (مک) یا PowerShell (ویندوز):

```bash
git clone https://github.com/mehdi2044/HodaSite.git
cd HodaSite
```

### B3. تنظیمات محیط

```bash
cp .env.example .env
```

فایل `.env` را با یک ویرایشگر باز کنید. برای لپ‌تاپ **هیچ چیزی لازم نیست عوض کنید** (مقدارهای پیش‌فرض کار می‌کنند). فقط این دو خط را نگاه کنید:

```
ADMIN_EMAIL=owner@example.com
ADMIN_PASSWORD=ChangeMe123!
```

اینها ایمیل و رمز اولین ادمین هستند؛ می‌توانید عوض کنید.

### B4. اجرا

```bash
docker compose -f docker-compose.dev.yml up --build
```

اولین بار ۵–۱۰ دقیقه طول می‌کشد (پکیج‌ها دانلود می‌شوند). وقتی خط `✓ Ready` را دیدید:

- فروشگاه: http://localhost:3000
- ادمین: http://localhost:3000/admin
- فایل‌ها (MinIO): http://localhost:9001 (کاربر/رمز در `.env`)

توقف: `Ctrl + C`. حذف کامل و شروع از صفر (داده‌های تست پاک می‌شود):

```bash
docker compose -f docker-compose.dev.yml down -v
```

### B5. به‌روزرسانی بعد از merge هر فاز

```bash
git pull
docker compose -f docker-compose.dev.yml up --build
```

### B6. اجرای محلی روی ویندوز

این بخش دقیقاً همان دستورهایی است که روی لپ‌تاپ ویندوزی مهدی اجرا می‌شود (PowerShell). Docker Desktop باید نصب و روشن باشد (آیکون نهنگ در نوار وضعیت).

**روشن کردن سایت (بار اول یا بعد از تغییر کد):**

```powershell
docker compose -f docker-compose.dev.yml up --build
```

بار اول ۵–۱۰ دقیقه طول می‌کشد. وقتی خط `✓ Ready` را دیدید، سایت روی http://localhost:3000/fa بالاست.

**روشن کردن سریع (بدون تغییر کد، از دفعهٔ قبل):**

```powershell
docker compose -f docker-compose.dev.yml up -d
```

**خاموش کردن (دادهٔ آزمایشی حفظ می‌شود):**

```powershell
docker compose -f docker-compose.dev.yml stop
```

**پاک‌کردن کامل و شروع از صفر (دادهٔ آزمایشی پاک می‌شود):**

```powershell
docker compose -f docker-compose.dev.yml down -v
```

**دیدن لاگ‌ها (وقتی چیزی درست کار نمی‌کند):**

```powershell
docker compose -f docker-compose.dev.yml logs --tail=200 app
```

برای دنبال‌کردن زنده‌ی لاگ‌ها (تا `Ctrl+C` بزنید): همان دستور را با `-f` اضافه اجرا کنید: `docker compose -f docker-compose.dev.yml logs -f app`.

**اگر سایت بالا نیامد، به ترتیب این‌ها را چک کنید:**

1. `docker compose -f docker-compose.dev.yml ps` — همهٔ سرویس‌ها باید `Up` باشند (`postgres` باید `healthy` باشد).
2. لاگ `app` را ببینید (دستور بالا) و متن خطا را برای عامل اجرایی بفرستید.
3. **تداخل پورت روی ویندوز:** اگر قبلاً یک Postgres یا هر برنامهٔ دیگری روی همین کامپیوتر نصب بوده، ممکن است پورت‌های `3000` یا `5432`/`55432` را قبل از Docker گرفته باشد و اتصال به دیتابیس یا سایت اشتباه برود (بدون خطای واضح). برای بررسی: `netstat -ano | findstr :3000` (یا `:55432`) — اگر یک PID غیرمرتبط با Docker آنجا بود، همان برنامه پورت را گرفته؛ یا آن برنامه را ببندید یا پورت را در `docker-compose.dev.yml` عوض کنید.
4. اگر مطمئن نیستید فایل `.env` درست است: دوباره `cp .env.example .env` بزنید و مقدارهای لازم را پر کنید.

**ایمیل و رمز ادمین کجاست؟** در فایل `.env` (نه `.env.example`) دو خط زیر است:

```
ADMIN_EMAIL=...
ADMIN_PASSWORD=...
```

این‌ها فقط روی همین لپ‌تاپ هستند (`.env` هرگز commit نمی‌شود). **رمز و ایمیل سرور Production باید متفاوت از لپ‌تاپ باشند** — همان مقداری که اینجا برای تست محلی گذاشته‌اید را روی سرور واقعی دوباره استفاده نکنید (بخش C4 را ببینید).

### B7. اجرای `pnpm test` مستقیم روی لپ‌تاپ (نه داخل Docker)

با `docker compose -f docker-compose.dev.yml up` بالا، دیتابیس Postgres روی پورت `55432` هاست هم در دسترس است، اما `pnpm test` روی لپ‌تاپ به‌طور پیش‌فرض دنبال آدرس داخل شبکهٔ Docker (`DATABASE_URL` در `.env`) می‌گردد، نه پورت هاست. برای همین متغیر جدا `TEST_DATABASE_URL` وجود دارد (نمونه‌اش در `.env.example`، زیر بلوک Database) — رفتار `pnpm test` بسته به آن دقیقاً سه حالت دارد:

1. **`TEST_DATABASE_URL` در `.env` خالی/نبود:** تست‌های integration فقط **skip** می‌شوند (تست‌های unit عادی اجرا می‌شوند) و همین ابتدای خروجی این خط چاپ می‌شود:
   ```
   ℹ integration tests skipped: TEST_DATABASE_URL not set (unit tests only)
   ```
2. **`TEST_DATABASE_URL` تنظیم شده ولی Postgres در دسترس نیست:** اجرای `pnpm test` **fail** می‌شود (نه skip بی‌صدا) با پیام واضح که آدرس در دسترس نیست. یعنی اگر این مقدار را گذاشته‌اید، باید `docker compose -f docker-compose.dev.yml up` هم روشن باشد؛ وگرنه `pnpm test` عمداً قرمز می‌شود تا یادتان نرود.
3. **`TEST_DATABASE_URL` تنظیم و در دسترس است:** هر ۴۵ تست (unit + integration) واقعاً اجرا می‌شوند.

برای حالت ۳ (توصیه‌شده وقتی `docker compose -f docker-compose.dev.yml up` روشن است)، در `.env` مقدار `TEST_DATABASE_URL` را نگه دارید و همان‌طور اجرا کنید:

```powershell
pnpm test
```

اگر پیام fail را دیدید یعنی پورت `55432` توسط برنامهٔ دیگری اشغال شده یا استک روشن نیست (بخش B6، مورد ۳ بالا را ببینید).

## C) اجرا روی سرور (staging و production)

### C1. خرید سرور

- کاندیدای اول: **Hetzner Cloud** (hetzner.com) → Cloud → New Project → Add Server. Location: آلمان یا Helsinki. Image: **Ubuntu 24.04**. یک پلن با **۴ vCPU / ۸GB RAM** کافی است (اسم و قیمت پلن‌ها را در زمان خرید ببینید؛ عوض می‌شوند).
- **قبل از Production:** از یک نفر در ایران (بدون VPN)، یکی در ترکیه و یکی در کانادا بخواهید staging را باز کنند: صفحهٔ اصلی، عکس‌ها، ورود با کد ایمیل، خرید تا آپلود فیش. اگر از ایران باز نشد، هاست را عوض می‌کنیم (کد وابسته به هاست نیست).
- SSH key: اگر ندارید، Hetzner گزینهٔ Password می‌دهد (ایمیل می‌کند).
- Backups سرور Hetzner را هم روشن کنید (۲۰٪ هزینهٔ اضافه) — این لایهٔ سوم امنیت است.

### C2. دامنه

در پنل دامنه (مثلاً Cloudflare یا هر جای دیگر) دو رکورد **A** به IP سرور:

- `staging.yourdomain.com`
- `yourdomain.com` و `www.yourdomain.com`
  (اگر Cloudflare است، ابر نارنجی را برای شروع **خاموش** (DNS only) بگذارید تا SSL خودکار سرور راحت بگیرد؛ بعداً می‌توانید روشن کنید.)

### C3. نصب روی سرور (یک اسکریپت)

به سرور وصل شوید:

```bash
ssh root@<IP-سرور>
```

سپس (این اسکریپت را Claude Code در فاز ۰۰ ساخت):

```bash
curl -fsSL https://raw.githubusercontent.com/mehdi2044/HodaSite/main/scripts/server-setup.sh | bash
```

اسکریپت: Docker نصب می‌کند، کاربر `deploy` می‌سازد، فایروال را تنظیم می‌کند، مخزن را در `/opt/hodasite` می‌گیرد و از شما می‌پرسد:

- دامنه (staging.yourdomain.com)
- ایمیل ادمین و رمز
- توکن گیت‌هاب (برای مخزن خصوصی؛ در GitHub: Settings → Developer settings → Personal access tokens)
  بعد `docker compose up -d` را اجرا می‌کند. ۵ دقیقه بعد سایت روی https://staging.yourdomain.com بالاست.

### C4. تنظیم `.env` سرور

فایل `/opt/hodasite/.env` — مقادیر مهم:

> نکته: در `.env` کامنت درون‌خطی (`مقدار   # توضیح`) ننویسید؛ Docker Compose آن را جزو مقدار می‌خواند. توضیح‌ها را در خط جدا بگذارید.

```
APP_URL=https://staging.yourdomain.com
DATABASE_URL=postgresql://app:<رمز-قوی>@postgres:5432/app
AUTH_SECRET=<خروجی: openssl rand -base64 33>
# s3 = هر فضای S3-سازگار: MinIO داخل Compose، یا Cloudflare R2 در Production
STORAGE_PROVIDER=s3
# کلید API را از resend.com بگیرید
EMAIL_PROVIDER=resend
RESEND_API_KEY=...
# همان کلید رایگان نوسان که در ارزینو دارید
NAVASAN_API_KEY=...
CRON_SECRET=<یک-رشته-تصادفی>
MAINTENANCE_SECRET=<یک-رشته-تصادفی-دیگر>
# برای Production اجباری — یک سرویس جدا از هاست (Backblaze B2 / Cloudflare R2 / Wasabi)
BACKUP_OFFSITE_ENDPOINT=...
BACKUP_OFFSITE_KEY=...
BACKUP_OFFSITE_SECRET=...
```

**فایل `.env` را در یک Password Manager (مثل Bitwarden) کپی نگه دارید.** این فایل بکاپ خودکار نمی‌شود.

### C5. به‌روزرسانی سرور بعد از هر merge

```bash
ssh deploy@<IP>
cd /opt/hodasite && ./scripts/deploy.sh
```

`deploy.sh` قبل از به‌روزرسانی خودکار یک بکاپ امنیتی می‌گیرد، کد جدید را می‌گیرد، migration را (در کانتینر `migrate`) اجرا و سایت را بدون قطعی طولانی ری‌استارت می‌کند. اگر مشکلی شد: تا فاز ۰۵ که rollback خودکار اضافه می‌شود، با `scripts/backup/restore.sh` داخل کانتینر `ops` از همان بکاپ امنیتیِ پیش‌ازدیپلوی بازگردانی کنید.

### C6. Production

همان مراحل C3 با دامنهٔ اصلی روی همان سرور (پورت‌های داخلی متفاوت؛ اسکریپت خودش می‌پرسد `staging` یا `production`) یا یک سرور جدا. پیشنهاد: تا Checkpoint 2 فقط staging.

## D) کارهای روزمره

### D1. بکاپ

- خودکار هر شب ۰۳:۳۰. وضعیت در **ادمین → System → Backups** و **System Health**. اگر کپی خارجی (Off-site) شکست بخورد، بکاپ محلی سالم می‌ماند ولی هشدار **قرمز** می‌بینید — نادیده نگیرید.
- بکاپ فوری: ادمین → Backups → **Backup now** یا در سرور: `./scripts/backup/backup.sh --label before-price-change`.
- دانلود: از همان صفحه. فایل zip را جایی امن نگه دارید.

### D2. بازگردانی (Restore)

- ادمین → Backups → انتخاب بکاپ (یا Upload backup) → **Request restore** → رمز + کد MFA. لاگ زنده را می‌بینید.
- یا در سرور: `docker compose exec ops ./scripts/backup/restore.sh /backups/2026-09-15_0330_scheduled --yes` (کانتینر ops خودش migration را اجرا می‌کند؛ به Docker دسترسی ندارد)
- سیستم اول از وضع فعلی بکاپ می‌گیرد، سایت را چند دقیقه در حالت تعمیرات می‌برد، بازگردانی می‌کند، سلامت را بررسی می‌کند و برمی‌گردد. اگر وسط کار مشکلی شد، سایت در حالت تعمیرات می‌ماند و داده‌های قبلی دست‌نخورده است — متن لاگ را برای عامل اجرایی بفرستید.

### D3. نرخ تومان

نرخ از **نوسان** خودکار گرفته می‌شود و در **ادمین → Pricing → FX** به‌صورت «نرخ پیشنهادی» کنار «نرخ فعال» نمایش داده می‌شود؛ با یک کلیک Accept کنید (یا دستی نرخ دیگری بزنید). اگر نرخ جدید بیش از ۵٪ پرش داشت، خودکار اعمال نمی‌شود و از شما تأیید می‌خواهد. لیر و دلار کانادا کاملاً خودکار است. اگر نرخ فعال قدیمی شود، بالای ادمین هشدار می‌بینید.

انتخاب ارائه‌دهنده، فیلد `usd_sell`/`usd_buy` و فاصلهٔ دریافت از خود صفحهٔ **Pricing → FX** تنظیم می‌شوند و نیازی به تغییر فایل محیط ندارند. فقط کلید محرمانهٔ `NAVASAN_API_KEY` در `.env` سرور قرار می‌گیرد؛ اگر هنوز کلید ندارید، ارائه‌دهندهٔ تومان را در همان صفحه روی «دستی» بگذارید و نرخ را با تأیید صریح ثبت کنید.

### D4. اگر سایت بالا نیامد

1. ادمین → System Health را ببینید (اگر باز می‌شود).
2. در سرور: `docker compose ps` و `docker compose logs --tail=200 app`.
3. متن خطا را برای عامل اجرایی بفرستید.

## اجرای فاز ۰۰ روی لپ‌تاپ

```bash
cp .env.example .env
docker compose -f docker-compose.dev.yml up --build
```

بار اول، migration و seed خودکار اجرا می‌شوند. سایت در `http://localhost:3000/fa`، پنل در `http://localhost:3000/admin` و ایمیل آزمایشی در `http://localhost:8025` است.

برای خاموش‌کردن و پاک‌کردن کامل دادهٔ آزمایشی:

```bash
docker compose -f docker-compose.dev.yml down -v
```

### اصلاحات فاز ۰۳ — ورود موجودی و نرخ تاریخی

- فایل موجودی باید دقیقاً چهار ستون `sku,quantity,unitCost,currency` و ۱ تا ۱۰۰۰ سطر داده داشته باشد؛ حداکثر حجم ۲ مگابایت است. اگر هر سطر نامعتبر باشد، هیچ سطری ثبت نمی‌شود. هنگام تعمیرات، ورود فایل متوقف می‌شود.
- برای افزایش موجودی از فرم اصلاح، بهای واحد و ارز را هم وارد کنید؛ افزایش یک دستهٔ خرید تازه می‌سازد. کاهش موجودی از قدیمی‌ترین دسته‌های همان انبار کم می‌کند و سوابق حرکت کالا حفظ می‌شوند.
- تاریخ خرید گذشته فقط با نرخ پذیرفته‌شده یا نرخ دستی معتبر همان تاریخ قابل ثبت است. در نبود سابقهٔ نرخ، ابتدا نرخ تاریخیِ معتبر را با بازهٔ زمانی و یادداشت ثبت کنید؛ نرخ امروز به خرید گذشته نسبت داده نمی‌شود.
- در ارتقا از فاز ۰۲، migration افزوده‌شده نرخ‌های معتبر تنظیم‌شده را منتقل می‌کند. برای ارتقای محیط دارای داده، seed نمایشی اجرا نکنید.
- سیاست پذیرش خودکار/تأیید مدیر از صفحهٔ نرخ ارز برای هر بازار قابل تغییر است و تغییر آن در سابقه ثبت می‌شود.


### آزمایش خرید و ایمیل — فاز ۰۴
1. با Docker Compose توسعه، Mailpit هم اجرا می‌شود. صندوق آزمایشی را در `http://localhost:8025` باز کنید؛ پیام‌ها از این محیط به اینترنت ارسال نمی‌شوند.
2. در فروشگاه محصولی به سبد اضافه کنید و با یک ایمیل نمونه مانند `buyer@example.com` وارد شوید. کد یا لینک ورود را از Mailpit بردارید؛ کد ده دقیقه اعتبار دارد و پس از پنج تلاش نادرست باید کد تازه بگیرید.
3. خرید شامل آدرس، بررسی هزینه و تأیید قوانین است. رسید نمونه PDF یا تصویر تا ۵ مگابایت بارگذاری کنید. در مدیریت، بخش سفارش‌ها امکان تأیید یا رد با دلیل و تمدید رزرو را دارد.
4. از بخش حساب‌های بانکی، اطلاعات و راهنمای هر بازار را ویرایش کنید؛ اطلاعات seed آزمایشی است. مهلت رزرو و پرداخت و اجازه خرید مهمان در تنظیمات خرید قابل تغییر است.
5. برای ارسال واقعی هنگام استقرار، `APP_URL` را به آدرس عمومی HTTPS، `EMAIL_PROVIDER` را به `smtp` یا `resend` و `EMAIL_FROM` را به فرستنده تأییدشده تنظیم کنید. برای SMTP از `SMTP_HOST`، `SMTP_PORT`، `SMTP_USER`، `SMTP_PASSWORD` و در صورت نیاز `SMTP_SECURE=true` استفاده کنید؛ برای Resend فقط `RESEND_API_KEY` لازم است. کلیدها فقط در محیط سرور می‌مانند.
6. پردازش ایمیل به cron موجود وابسته است. اگر پیامی نیامد، وضعیت Job و SystemAlert را بررسی کنید. رسیدها خصوصی‌اند و لینک نمایش پس از ده دقیقه منقضی می‌شود؛ برای لینک تازه صفحه سفارش را دوباره باز کنید.
7. خرید هاست و دامنه می‌تواند نزدیک انتشار باشد؛ تست بازگردانی بکاپ و ارسال ایمیل واقعی در محیط نهایی همچنان پیش از انتشار لازم است.


### ورود دومرحله‌ای مدیر — فاز ۰۵
1. پس از ارتقا، نشست‌های قدیمی مدیر معتبر نیستند؛ دوباره با ایمیل و رمز وارد شوید. حساب مالک/مدیر ابتدا به صفحهٔ راه‌اندازی دومرحله‌ای هدایت می‌شود.
2. رمز را تأیید کنید، QR را با برنامهٔ Authenticator اسکن کنید و کد شش‌رقمی را وارد کنید. QR در خود برنامه ساخته می‌شود و برای سرویس خارجی ارسال نمی‌شود.
3. ده کد بازیابی را در محل امن ذخیره کنید؛ فقط یک‌بار نمایش داده می‌شوند و هرکدام یک‌بار مصرف‌اند. سپس با کد تازهٔ برنامه یا یک کد بازیابی وارد شوید. کدی که برای فعال‌سازی استفاده شد دوباره پذیرفته نمی‌شود.
4. در «امنیت حساب» دستگاه‌ها/نشست‌های فعال را ببینید و نشست دلخواه یا دیگر دستگاه‌ها را خارج کنید. غیرفعال‌کردن کاربر و تغییر نقش نیز نشست‌های او را باطل می‌کند.
5. اگر کد درست پذیرفته نشد، ساعت گوشی را خودکار کنید و منتظر کد تازه بمانید؛ تلاش‌های پی‌درپی محدود می‌شوند.
6. AUTH_SECRET علاوه بر امضای نشست برای رمزگشایی credential شخصی MFA و پیام‌های صف استفاده می‌شود. آن را همراه تنظیمات عملیاتی به‌صورت امن و جدا از مخزن نگه دارید. تعویض آن بدون برنامهٔ انتقال کلید، ورود دومرحله‌ای و پیام‌های صف را از کار می‌اندازد.
7. هاست و دامنه برای توسعه و این تست‌ها لازم نیست؛ پذیرش HTTPS و ایمیل و بکاپ off-site واقعی همچنان پیش از انتشار انجام می‌شود.

### ارسال بسته و رهگیری مشتری (بخش ارسال فاز ۰۵)

- پس از پرداخت تأییدشده، سفارش را در مدیریت باز کنید. در بخش «ارسال»، مسیر و تعداد کالاهای همان بسته را انتخاب و بسته را بسازید. برای ارسال جزئی، تعداد کمتر وارد کنید؛ باقیمانده را در بستهٔ بعدی بفرستید.
- در «تنظیمات ارسال» مسیرهای هر بازار، نام مرحله به سه زبان، شرکت حمل و الگوی لینک رهگیری قابل ویرایش است. مسیر پیش‌فرض باید فعال بماند؛ برای جایگزینی، مسیر دیگری را پیش‌فرض کنید. تغییر تنظیمات، بسته‌های ساخته‌شده را تغییر نمی‌دهد.
- در هر مرحله شرکت حمل، کد رهگیری، هزینه و ارز، وضعیت و تاریخ‌ها را ثبت کنید. تاریخ‌های فرم UTC هستند. تاریخ خالیِ شروع یا تحویل، زمان همان ثبت را می‌گیرد. هزینه پس از شروع مرحله قفل می‌شود. مرحلهٔ بعد پس از تحویل مرحلهٔ قبل آغاز می‌شود.
- مرحلهٔ اجرا‌نشده را می‌توان لغو کرد یا مرحله‌ای به انتهای مسیر افزود. بستهٔ شروع‌نشده نیز قابل لغو است؛ سوابق آن حذف نمی‌شود. بستهٔ دیگری با تعداد آزادشده بسازید.
- یادداشت رهگیری برای مشتری نمایش داده می‌شود؛ اطلاعات داخلی یا شخصی را در آن ننویسید. وضعیت کل سفارش پس از اولین ارسال «ارسال‌شده» و پس از تحویل همهٔ کالاهای همهٔ بسته‌ها «تحویل‌شده» می‌شود.
- مشتری در صفحهٔ سفارش یا مسیر `/fa/tracking`، `/tr/tracking` و `/en/tracking` رهگیری را می‌بیند. رهگیری عمومی شماره سفارش و ایمیل ثبت‌شده را می‌خواهد و آدرس، هزینهٔ حمل یا یادداشت داخلی را نشان نمی‌دهد.
- قالب ایمیل شروع ارسال و تحویل در تنظیمات اعلان‌ها قابل ویرایش است. اتصال خودکار به شرکت حمل در این بخش فعال نشده؛ اطلاعات حمل به‌صورت دستی ثبت می‌شود. خرید هاست و دامنه برای ادامهٔ توسعه لازم نیست.

### فاکتور PDF خصوصی (فاز ۰۵)
- پس از تأیید پرداخت، کران موجود `/api/cron/tick` فاکتور را تولید می‌کند؛ `CRON_SECRET` باید تنظیم باشد. پنل سفارش وضعیت و لینک دانلود و دکمهٔ نسخهٔ جدید دارد. مدیر برای صدور مجدد هم مجوز مشاهدهٔ فاکتور و هم ویرایش سفارش همان بازار را لازم دارد.
- تنظیم عنوان شناسهٔ مالیاتی فارسی/ترکی/انگلیسی و شناسهٔ فروشنده: `/admin/settings/invoices` (لینک در صفحهٔ بازارها). برند و لوگو از تنظیمات برند/تم و متن‌ها از ویرایشگر ترجمه می‌آیند. این فیلدها جایگزین الزامات صدور فاکتور قانونی هر کشور نیستند.
- Docker مرورگر Chromium را نصب می‌کند و `INVOICE_CHROMIUM_PATH=/usr/bin/chromium` دارد. در توسعه، `pnpm exec playwright install --with-deps chromium` و `node scripts/prepare-invoice-fonts.mjs` را اجرا کنید؛ یا مسیر مرورگر نصب‌شده را در متغیر محیطی بالا بگذارید. فرمان build فونت‌ها را خودکار آماده می‌کند. اطلاعات مشتری به سرویس PDF خارجی ارسال نمی‌شود.
- فاکتورهای قدیمی با تغییر قیمت و نرخ ارز تغییر نمی‌کنند. صدور مجدد، نسخهٔ تازه با تنظیمات برند/فیلد مالیاتی تازه و همان snapshot مالی نخست می‌سازد؛ فایل نسخه‌های قبلی حفظ می‌شود. سفارش‌های پرداخت‌شده پیش از این قابلیت، با دکمهٔ صدور نسخهٔ جدید اولین فاکتور را می‌گیرند.
- فایل‌ها در مسیر خصوصی `invoices/` در همان StorageProvider و بکاپ رسانه ذخیره می‌شوند؛ آن‌ها را از تنظیمات bucket یا reverse proxy عمومی نکنید. خروجی URL عمومی و لینک اشتراکی بدون بررسی مالکیت ندارد.
- وضعیت ناموفق: مسیر Chromium، فونت‌ها، فضای آزاد و صف کران را بررسی کنید؛ سیستم تلاش مجدد محدود دارد و مدیر می‌تواند نسخهٔ تازه درخواست کند. اگر نتیجهٔ commit انتشار نامعلوم شود، فایل تلاش حفظ می‌شود تا سند منتشرشده اشتباهاً حذف نشود؛ چنین فایل یتیمی ممکن است نیازمند پاک‌سازی عملیاتی بعدی باشد.

### تغییر روش ساخت سرویس فایل
تصویر آمادهٔ قدیمی MinIO و نشانی دانلود قدیمی ابزار آن در بررسی CI در دسترس نبودند. نسخهٔ جدید پروژه سرویس فایل را از انتشار رسمی دارای اصلاح امنیتی می‌سازد؛ اولین `docker compose ... up -d --build` ممکن است بیشتر طول بکشد و به اینترنت نیاز دارد. نام volumeها تغییر نکرده است؛ برای به‌روزرسانی نیازی به حذف داده‌ها یا اجرای `down -v` نیست.

### بازیابی فایل‌ها در حالت S3
نسخهٔ جدید برای بازیابی، فایل‌ها را در یک نسل تازه قرار می‌دهد و پس از بررسی فعال می‌کند. سرویس app و ops باید volume مشترک `/data` و مقدار یکسان `S3_PREFIX_FILE` داشته باشند؛ Compose موجود این volume را مشترک دارد. فایل اشاره‌گر را دستی حذف یا ویرایش نکنید و بعد از اولین بازیابی S3 به نسخهٔ قدیمی برنامه برنگردید. فایل‌های نسل قبلی برای بازیابی احتمالی حفظ می‌شوند؛ پاک‌سازی آن‌ها باید در برنامهٔ نگهداری زیرساخت بررسی شود. این قابلیت به معنی خرید هاست یا فعال‌شدن بکاپ خارج از سرور نیست.

### پنل بکاپ — فاز ۵
پس از دریافت نسخهٔ جدید، کانتینرهای `app` و `ops` را با همان پروژه و فایل‌های Compose فعلی بازسازی و اجرا کنید. داده‌ها و volumeها را حذف نکنید. سرویس `ops` باید روشن بماند؛ در غیر این صورت درخواست‌ها در صف می‌مانند.

مالک در «بکاپ و بازیابی» می‌تواند نسخه بسازد، سلامت آن را بررسی کند و فایل ZIP دریافت کند. فایل بارگذاری‌شده ابتدا بررسی می‌شود و فقط پس از «آماده» شدن قابل بازیابی است. بازیابی به رمز عبور و کد تازهٔ برنامهٔ احراز هویت نیاز دارد؛ کد بازیابی ورود جایگزین این کد نیست. قبل از جایگزینی، بکاپ ایمنی ساخته می‌شود.

زمان‌بندی را در همین صفحه فعال و ذخیره کنید. ساعت‌ها به وقت UTC هستند و مقدار صفر برای روز بررسی یعنی یکشنبه. نگهداری خودکار فقط نسخه‌های زمان‌بندی‌شدهٔ محلی را پاک‌سازی می‌کند؛ نسخه‌های دستی، ایمنی و کپی خارج از سرور حفظ می‌شوند. رمز و مشخصات سرویس خارج از سرور همچنان فقط در تنظیمات محیطی قرار می‌گیرند.


### به‌روزرسانی با بازگشت خودکار — فاز ۰۵ / D43
این روش برای نصب موجود روی میزبان Linux با Docker Compose و `flock` است؛ نصب نخست همچنان از دستورهای Compose همین راهنما انجام می‌شود. پیش از استفاده، نسخهٔ app/ops باید بازیابی نسل‌های S3 را پشتیبانی کند. فایل `.env` و مقصد دیتابیس/رسانه هنگام این عملیات نباید تغییر کنند؛ مهاجرت سرور یا دیتابیس یک کار جداگانه است.

۱. کد تأییدشده را دریافت کنید و مطمئن شوید فایل‌های tracked تغییر محلی ندارند.
۲. روی میزبان، دستور `bash scripts/deploy.sh` را اجرا کنید. ساخت image پیش از توقف فروش انجام می‌شود. سپس ops/cron متوقف، حالت تعمیرات تأیید، درخواست‌های جاری تخلیه و بکاپ ایمنی کامل و اعتبارسنجی‌شده گرفته می‌شود. فقط بعد از این مراحل، migration و نسخهٔ تازه اجرا می‌شوند.
۳. اگر نسخهٔ تازه پیش از بازشدن فروش شکست بخورد، imageهای قبلی و داده‌های بکاپ از داخل ops برمی‌گردند. کد خروج ۴۲ یعنی «استقرار تازه ناموفق بود، بازگشت موفق شد»؛ کد ۴۳ یعنی بازیابی نیز نیازمند بررسی دستی است. موفقیت استقرار کد خروج صفر دارد. پس از بازشدن فروش، خطای راه‌اندازی worker هرگز باعث برگشت داده‌ها و حذف خریدهای تازه نمی‌شود؛ worker را جداگانه دوباره راه بیندازید.
۴. وضعیت هر تلاش، imageهای دقیق قبلی/جدید و کلید بکاپ در `.deploy/releases/` نگه داشته می‌شود. فایل `.deploy/active.yml` نسخهٔ پذیرفته‌شده را مشخص می‌کند. برای راه‌اندازی مجدد بدون ساخت دوباره، از `docker compose -f docker-compose.yml -f .deploy/active.yml up -d --no-build` استفاده کنید. imageهای `previous-*` و بکاپ ایمنی را تا بررسی دستی حذف نکنید.
۵. قطع برق یا SIGKILL قابل مدیریت با trap نیست؛ اگر وضعیت نیمه‌تمام ماند، همان کلید بکاپ و imageهای محفوظ را با روش بازیابی ops بررسی کنید. این محدودیت با «بازگشت خودکار هنگام خطای قابل تشخیص» فرق دارد و پذیرش عملیاتی روی staging همچنان لازم است.

نسخهٔ آمادهٔ image نیز با دو آرگومان `--app-image sha256:... --ops-image sha256:...` قابل استفاده است؛ فقط شناسهٔ تغییرناپذیر image محلی پذیرفته می‌شود، نه tag شناور. این بخش هیچ استقرار واقعی یا خرید زیرساختی را انجام نمی‌دهد.


### زبان پنل و هشدارهای سلامت
پس از ورود، انتخاب زبان در منوی پنل قرار دارد. فارسی راست‌به‌چپ و ترکی/انگلیسی چپ‌به‌راست نمایش داده می‌شوند؛ انتخاب شما در همین مرورگر حفظ می‌شود و زبان آدرس فروشگاه را تغییر نمی‌دهد.

نشان هشدارها برای کاربر دارای مجوز سلامت، به صفحهٔ «سلامت سیستم» می‌رود. هشدارهای بکاپ قدیمی، همگام‌سازی خارج سرور، نرخ ارز قدیمی، موجودی کم، پرداخت عقب‌افتاده و کارهای ناموفق با اجرای cron به‌روز می‌شوند. پس از رفع علت، هشدار جاری بسته می‌شود و سابقه باقی می‌ماند. وضعیت ایمیل فقط تنظیم اتصال را نشان می‌دهد؛ ارسال واقعی باید در staging آزموده شود.

اگر در انتشار وضعیت `REOPEN_UNCONFIRMED` ثبت شد، ممکن است فرمان بازشدن فروش اجرا شده و فقط پاسخ آن نرسیده باشد. نسخهٔ تازه و داده‌های آن را حفظ کنید؛ ابتدا وضعیت تعمیرات و سپس workerها را بررسی کنید. در این وضعیت اجرای خودکار بازیابی بکاپ قدیمی مجاز نیست.


### وب‌اپ موبایل — فاز ۵b
پس از دریافت نسخهٔ جدید پروژه، وابستگی‌ها را نصب و برنامه را دوباره build/start کنید؛ تغییر فایل‌ها به‌تنهایی نسخهٔ Docker قبلی را عوض نمی‌کند. نصب روی گوشی از نشانی HTTPS معتبر انجام می‌شود؛ HTTP با IP شبکهٔ محلی جایگزین آن نیست. راهنمای نصب سه‌زبانه در پایین فروشگاه قرار دارد. نام و آیکون نصب از تنظیمات برند و لوگو/فاویکون پنل گرفته می‌شوند؛ پس از تغییر نام یا آیکون، نمایش نسخهٔ جدید آیکون ممکن است به نصب دوباره در مرورگر نیاز داشته باشد.

در اندروید راهنمای منوی مرورگر و در آیفون راهنمای Safari و «افزودن به صفحهٔ اصلی» نمایش داده می‌شود. هنگام قطع اینترنت، ثبت سفارش و تغییرات متوقف می‌شود و درخواست مالی در صف آفلاین ذخیره نمی‌شود. برای دریافت نسخهٔ تازه، کار جاری را تمام کنید، پنجره‌های دیگر فروشگاه را ببندید و از صفحهٔ خانه دکمهٔ به‌روزرسانی را بزنید.

آزمون مرورگر برای توسعه‌دهنده: `pnpm exec playwright install --with-deps chromium webkit` و سپس `pnpm e2e` با دیتابیس/ایمیل تست طبق تنظیمات CI. نصب روی گوشی واقعی باید جداگانه طبق `docs/phases/phase-05b-device-acceptance.md` ثبت شود.

### نصب و آزمون روی گوشی اندروید

نسخهٔ فعلی یک وب‌اپ نصب‌شدنی (PWA) است. از داخل Chrome نصب می‌شود؛ فایل APK یا انتشار در Google Play در این مرحله نداریم. آیکون روی گوشی ایجاد می‌شود و برنامه باید در پنجرهٔ مستقل باز شود. خرید همچنان به اتصال به سرور نیاز دارد.

**نصب برای آزمون نهایی:**

1. ابتدا نسخهٔ جدید پروژه باید روی محیط آزمایشی با آدرس HTTPS معتبر اجرا شود؛ ادغام در GitHub به‌تنهایی سایت روی لپ‌تاپ یا سرور را به‌روزرسانی نمی‌کند. خرید دامنه و هاست شرط ادامهٔ توسعه نیست، اما محیط آزمون نهایی هنوز باید آماده شود.
2. آدرس آزمایشی را مستقیماً در Chrome گوشی باز کنید. برای فارسی و بازار ایران مسیر `/fa/m/IR`، برای ترکی `/tr/m/TR` و برای انگلیسی `/en/m/CA` را انتخاب کنید.
3. منوی سه‌نقطه → «Install and create shortcut» → «Install». در بعضی نسخه‌ها عنوان «Install app» یا «Add to Home screen» دیده می‌شود؛ گزینهٔ نصب را انتخاب کنید. راهنمای نصب پایین فروشگاه هم در دسترس است. ساخت میان‌بر به‌تنهایی اثبات نصب مستقل نیست.
4. از مرورگر خارج شوید و آیکون فروشگاه را لمس کنید. نام، آیکون، نبود نوار آدرس مرورگر و حفظ زبان و بازار را بررسی کنید.

**بررسی محلی روی اندروید بدون هاست، با کابل USB:**

1. سایت روی لپ‌تاپ در `http://localhost:3000/fa` اجرا و قابل بازکردن باشد؛ لپ‌تاپ و برنامه هنگام آزمون روشن بمانند.
2. در گوشی، Developer options و USB debugging را فعال کنید، با کابل داده به لپ‌تاپ وصل شوید و اجازهٔ اتصال این کامپیوتر را روی گوشی تأیید کنید.
3. در Chrome لپ‌تاپ `chrome://inspect/#devices` را باز کنید. Discover USB devices را فعال کنید و صبر کنید گوشی در فهرست ظاهر شود.
4. Port forwarding را باز کنید؛ پورت سمت گوشی `3000` و مقصد سمت لپ‌تاپ `localhost:3000` باشد. Enable port forwarding را فعال کنید.
5. در Chrome گوشی `http://localhost:3000/fa/m/IR` را باز کنید. این localhost با انتقال پورت USB به لپ‌تاپ وصل می‌شود؛ نوشتن localhost بدون این تنظیم به لپ‌تاپ دسترسی نمی‌دهد. دسترسی به IP لپ‌تاپ با HTTP نیز آزمون نهایی نصب امن محسوب نمی‌شود.
6. این روش برای بررسی لمس، اندازهٔ متن، کیبورد و مسیر خرید محلی است. اگر مرورگر نصب محلی را عرضه کرد، نتیجه را «آزمون محلی» ثبت کنید؛ پذیرش نهایی HTTPS و به‌روزرسانی دو build همچنان جداست. با قطع کابل یا خاموشی لپ‌تاپ، دسترسی به سرور محلی قطع می‌شود. پس از پایان، انتقال پورت و USB debugging را خاموش کنید.

**چه چیزهایی را تست کنیم؟**

- هر سه زبان و بازار؛ انتخاب رنگ/سایز، افزودن و حذف سبد، نمایش درست مبلغ و حفظ بازار.
- باز و بسته‌کردن برنامه، چرخاندن گوشی، بزرگ‌کردن متن و ورود اطلاعات با کیبورد، بدون پوشاندن دکمه‌ها.
- سفارش و فیش صرفاً آزمایشی؛ در قطع ارتباط، ثبت سفارش نباید پنهانی صف‌بندی شود و صفحهٔ آفلاین نباید اطلاعات خصوصی نشان دهد. در اتصال USB، حالت پرواز به‌تنهایی تضمین قطع مسیر USB نیست؛ برای این بخش از محیط HTTPS با قطع واقعی شبکه استفاده کنید.
- پس از استقرار build دوم: وجود پنجرهٔ دیگر به‌روزرسانی را عقب بیندازد؛ پس از پایان کار و بستن پنجره‌های دیگر، دکمهٔ به‌روزرسانی در خانهٔ همان بازار کار کند. این آزمون به دو نسخهٔ buildشده نیاز دارد؛ تغییر زندهٔ کد در حالت توسعه کافی نیست.

منابع رسمی: [نصب وب‌اپ در Chrome اندروید](https://support.google.com/chrome/answer/9658361?co=GENIE.Platform%3DAndroid&hl=en)، [انتقال پورت USB در Chrome](https://developer.chrome.com/docs/devtools/remote-debugging/local-server/).


### عیب‌یابی ورود مدیر و نسخهٔ محلی (۲۰۲۶-۰۹-۱۲)
دکمهٔ «نمایش رمز / مخفی کردن رمز» در صفحهٔ ورود مدیر است. این دکمه فرم را ارسال نمی‌کند و پس از تلاش برای ورود، رمز دوباره مخفی می‌شود. برای ورود از حساب مدیر استفاده کنید؛ ساخت حساب در فروشگاه، حساب مدیر نمی‌سازد.

**به‌روزرسانی امن روی PowerShell، در پوشهٔ پروژه با Docker Desktop روشن:**
```powershell
git switch main
git pull --ff-only
docker compose -f docker-compose.dev.yml run --rm --no-deps app pnpm install --frozen-lockfile
docker compose -f docker-compose.dev.yml up -d --build --force-recreate
```
حذف volume یا `down -v` لازم نیست. اگر git به خاطر تغییر محلی متوقف شد، از دستور force یا reset برای ردکردن آن استفاده نکنید؛ ابتدا تغییر محلی را بررسی کنید. پس از Ready شدن app، صفحه را با Ctrl+Shift+R تازه کنید.

**تشخیص علت ورود بدون نمایش رمز، ایمیل یا راز دومرحله‌ای:**
```powershell
docker compose -f docker-compose.dev.yml exec app pnpm exec tsx scripts/admin-login-check.ts
```
این فرمان حساب تنظیم‌شده در محیط کانتینر را بررسی می‌کند. اگر ایمیل واردشده در مرورگر متفاوت است، می‌توانید همان ایمیل را به‌عنوان آخرین آرگومان در رایانهٔ خود اضافه کنید؛ ایمیل واقعی را در مخزن عمومی یا گزارش عمومی درج نکنید. خروجی فرمان فقط وضعیت‌ها و تعدادهاست؛ رمز یا کد احراز هویت را برای کسی ارسال نکنید. این فرمان هیچ حساب، رمز، نشست، محدودیت ورود یا دادهٔ مالی را تغییر نمی‌دهد.

| خروجی | معنی و اقدام |
| --- | --- |
| `adminAccountFound: false` | حساب مدیر با این ایمیل در دیتابیس فعلی نیست. `customerAccountOnly: true` یعنی فقط حساب مشتری موجود است. ایمیل مدیر را با تنظیمات اولیه مقایسه کنید. |
| `configuredPasswordMatches: false` | رمز فعلی تنظیمات با رمز ذخیره‌شده فرق دارد. seed فقط حسابِ جدید می‌سازد؛ عوض‌کردن ADMIN_PASSWORD رمز حساب موجود را تغییر نمی‌دهد. از رمز ذخیره‌شدهٔ قبلی یا مسیر مجاز تغییر رمز توسط مدیر استفاده کنید. |
| `configuredPasswordMatches: null` | حساب یکتا پیدا نشده یا ایمیل انتخابی با حساب تنظیمات متفاوت است؛ این خروجی به‌معنی غلط‌بودن رمز واردشده نیست. |
| `mfaEnabled: true` | باید کد شش‌رقمی برنامهٔ احراز هویت یا کد بازیابی استفاده‌نشده را وارد کنید؛ خالی گذاشتن کد پذیرفته نیست. |
| `mfaSecretReadable: false` | راز فعال دومرحله‌ای با AUTH_SECRET فعلی قابل خواندن نیست یا داده ناقص است؛ تنظیمات AUTH_SECRET قبلی و بکاپ را بررسی کنید، MFA را برای عبور از خطا حذف نکنید. |
| `accountRateLimitWaitSeconds` بزرگ‌تر از صفر | این تعداد ثانیه تا پایان محدودیت حساب باقی مانده است. محدودیت IP جداگانه است و در این فرمان سنجیده نمی‌شود. |
| `accountActive: false` | حساب غیرفعال شده است. |
| `storedEmailCaseMismatch` یا `ambiguousEmailCase` | حروف بزرگ/کوچکِ ایمیل ذخیره‌شده یا حساب‌های هم‌نام باید توسط مدیر بررسی شوند. |
| `localStorefront.mobileNavigationPresent` و `pwaManifestLinked` هر دو true | HTML زندهٔ محلی نشانگرهای ظاهر موبایل و PWA را دارد؛ این بررسی، نصب واقعی گوشی را اثبات نمی‌کند. |
| `localStorefront.reachable: false` | برنامه هنوز آماده نیست، در حالت تعمیرات است یا پاسخ موفقی از پورت ۳۰۰۰ نیامده است. |

کارت‌های یک‌رنگِ «محصول نمونه» عکس‌های تولیدشده توسط seed هستند، نه خطای دانلود عکس. تغییر کد، محتوای نمونهٔ دیتابیس را با عکس لباس عوض نمی‌کند؛ عکس‌های واقعی باید از کتابخانهٔ رسانه به محصولات و بنرها متصل شوند. تصویر دسکتاپ به‌تنهایی به‌روز بودن نسخه را ثابت نمی‌کند؛ نوار پایین و جست‌وجوی جدید را در عرض موبایل و نشانگرهای بالا بررسی کنید.

### به‌روزرسانی ظاهر در یک پیش‌نمایش Docker موجود
ابتدا `docker compose ls` را اجرا کنید. نام پروژه و **تمام فایل‌های Compose همان اجرای فعال** را در دستورهای بعدی استفاده کنید. بازکردن پوشه یا بستن PowerShell نام پروژهٔ Docker را تغییر نمی‌دهد و کانتینرهای پس‌زمینه را متوقف نمی‌کند. اجرای دوباره بدون نام/فایل قبلی می‌تواند پروژه و volume جدا بسازد و با پورت‌های 3000 و 55432 تداخل پیدا کند.

پس از دریافت آخرین `main`، از داخل کانتینر app فعال این دستور را اجرا کنید؛ `YOUR_APP_CONTAINER` را با نام واقعی همان کانتینر جایگزین کنید:

```powershell
docker exec YOUR_APP_CONTAINER pnpm exec tsx scripts/upgrade-demo-storefront.ts
```

این فرمان فقط تصاویر و ترکیب اولیهٔ نمونهٔ دست‌نخورده را ارتقا می‌دهد؛ حساب، رمز، موجودی، قیمت و سفارش را تغییر نمی‌دهد. کش صفحهٔ اصلی نسخهٔ رکوردهای دیتابیس را در هر درخواست بررسی می‌کند؛ پس از ارتقای محتوا، صفحه را دوباره باز کنید و برای تازه‌شدن این کش نیازی به restart نیست. ذخیره از پنل نیز کش Homepage را باطل می‌کند. برای این کار حذف volume یا اجرای دوبارهٔ seed عمومی لازم نیست. اگر تنظیمات override مسیر کد دیگری را mount می‌کند، همان مسیر واقعی باید نسخهٔ جدید را داشته باشد.

در صفحهٔ اصلی، تصویر بارانی، چهار دستهٔ تصویری و ردیف محصولات را ببینید. یک محصول را باز کنید، عکس را بزرگ کنید، رنگ/سایز را انتخاب کنید و افزودن به سبد را بررسی کنید. تصاویر با برچسب «نمایشی» برای قضاوت طراحی‌اند؛ از بخش رسانه/کاتالوگ با عکس واقعی کالا جایگزین شوند. بنر و دسته‌ای که قبلاً ویرایش کرده‌اید عمداً خودکار تغییر نمی‌کند. نصب واقعی اندروید و آیفون همچنان نیازمند آزمون HTTPS است.

### عملیات مالی فاز ۶
در مدیریت → گزارش مالی → عملیات مالی، بازار را انتخاب کنید. ابتدا تأمین‌کننده بسازید، سفارش خرید را با تعداد و **مبلغ کل ردیف** و نرخ تاریخ خرید وارد کنید. ثبت خرید پیش‌نویس است؛ تأیید دریافت، موجودی و سند حسابداری را با هم ایجاد می‌کند. هزینه ابتدا منتظر تأیید است؛ تأیید حسابدار سند را ثبت می‌کند. سرمایهٔ شریک نیز بعد از تأیید ثبت می‌شود. نرخ‌ها به معنی «لیر/دلار به ازای یک واحد ارز اصلی» هستند و تاریخ ورودی UTC است.
فعال‌سازی ثبت خودکار در تنظیم همان بازار فقط برای رویدادهای جدید است؛ سوابق قبلی خودکار وارد دفتر نمی‌شوند. پیش از شروع با دادهٔ واقعی، پذیرش مالی و نقطهٔ شروع باید تأیید شوند.
بکاپ دستی و بازیابی فایل: مدیریت → سیستم → بکاپ‌ها (`/admin/system/backups`). بکاپ فوری، دانلود و آپلود فایل وجود دارد؛ بازیابی توسط مالک با رمز و TOTP و در worker جداگانهٔ ops انجام می‌شود. پیش از جایگزینی اطلاعات، بکاپ ایمنی گرفته می‌شود. فایل `.env` حاوی کلیدها در بکاپ خودکار نیست و باید جداگانه امن نگهداری شود.

### امکانات تکمیل‌شدهٔ مالی در محیط محلی
در «گزارش مالی → عملیات مالی»، شروع حسابداری را برای هر بازار صریحاً فعال کنید و نرخ و تاریخ معتبر را وارد کنید. سوابق گذشته خودکار بازنویسی نمی‌شوند. ثبت خرید، دریافت موجودی، تأیید هزینه و سرمایهٔ شرکا همگی مرحلهٔ تأیید دارند. پیوست هزینه فقط PDF خصوصی است. برای هزینهٔ عمومی، حساب بدون محدودیت بازار لازم است؛ این هزینه در سود تجمیعی دیده می‌شود.

روش هزینهٔ پیش‌فرض FIFO است. انتخاب میانگین برای موجودی مشترک انبار، حساب بدون محدودیت بازار و موجودی با یک ارز اصلی می‌خواهد؛ پس از اولین ارزش‌گذاری قابل تغییر نیست. خطای دقت یا ارز متفاوت را با تغییر نرخ تاریخی دور نزنید. هزینهٔ افتتاحیه فقط واحدهای موجودیِ بدون لات را پوشش می‌دهد.

بکاپ دستی، دانلود، بارگذاری فایل بکاپ و درخواست بازیابی در «سیستم → بکاپ‌ها» قرار دارند. بازیابی از طریق سرویس جداگانهٔ ops انجام می‌شود. برای نصب نسخهٔ جدید، migration افزایشی اجرا می‌شود؛ حذف دیتابیس یا اجرای reset جزو به‌روزرسانی نیست. این مراحل نیازی به خرید هاست یا دامنه و انتشار سایت ندارند.

### راه‌اندازی دستیار هوش مصنوعی فاز ۷ در محیط محلی
کلید را فقط در فایل `.env` پروژه قرار دهید: برای جمنای `GEMINI_API_KEY` و در صورت نیاز نام جایگزین `GOOGLE_API_KEY`، برای ارائه‌دهندگان دیگر `OPENAI_API_KEY` یا `ANTHROPIC_API_KEY`. مقدار کلید را در گفت‌وگو، فرم مدیریت یا مخزن وارد نکنید. پس از تغییر محیط، برنامه را دوباره اجرا کنید. پنل فقط وجود کلید را نمایش می‌دهد؛ این علامت به معنی تأیید اتصال واقعی نیست.

در «تنظیمات هوش مصنوعی»، ارائه‌دهنده، شناسهٔ مدل اقتصادی و پیشرفته و قیمت ورودی/خروجی حساب خود به دلار برای یک میلیون توکن را وارد کنید. هشدار و سقف ماهانه را تنظیم و قابلیت موردنیاز را صریحاً فعال کنید. سقف برنامه بر پایهٔ برآورد است؛ سقف هزینهٔ حساب ارائه‌دهنده نیز مستقل تنظیم می‌شود. درخواست‌های دارای نتیجهٔ نامشخص، هزینهٔ رزروشده را آزاد نمی‌کنند. گزارش مصرف، وضعیت درخواست و مبلغ برآوردی را نشان می‌دهد. مدل‌های صفرقیمتِ پیش‌فرض تا تکمیل تنظیمات فعال نمی‌شوند.

در ویرایشگر محصول، عنوان و ویژگی‌های معلوم را بنویسید، حداکثر دو عکس انتخاب کنید و «ساخت پیشنهاد» را بزنید. استفادهٔ واقعی از تصویر نیاز به فعال‌بودن گزینهٔ تصویر در تنظیمات و در همان درخواست دارد. هر فیلد را بخوانید، ویرایش یا کنار بگذارید و فقط موارد درست را انتخاب کنید. «اعمال» پیشنهاد را وارد فرم می‌کند؛ برای ثبت نهایی، دکمهٔ ذخیرهٔ محصول را بزنید. وضعیت انتشار و قیمت با دستیار تغییر نمی‌کنند. متن‌های جایگزین تصویر و کلیدواژه‌های سئو نیز قابل بازبینی‌اند.

برای کار گروهی به «صف بازبینی هوش مصنوعی» بروید و حداکثر ۲۰ پیش‌نویس را انتخاب کنید. پردازش با صف موجود و cron برنامه انجام می‌شود؛ صفحه را پس از پردازش تازه کنید. اعمال پیشنهاد صف فقط فیلدهای تأییدشده را ذخیره می‌کند و اگر محصول در این فاصله تغییر کرده باشد، از بازنویسی جلوگیری می‌شود. تحلیل مالی نیز فقط جمع‌های گزارش را می‌خواند و سندی ثبت نمی‌کند.

آزمون واقعی با کلید لپ‌تاپ: یک عنوان پالتوی پشمی و دو عکس آزمایشی وارد کنید؛ زمان پاسخ و ثبت هزینه را بسنجید، ابتدا بدون اعمال از صفحه خارج شوید و عدم تغییر محصول را بررسی کنید. سپس چند فیلد را انتخاب و ذخیره کنید. تغییر ارائه‌دهنده را فقط با کلید و مدل معتبر همان حساب بررسی کنید. تست‌های خودکارِ پاسخ ساختگی جای این آزمون اتصال و معیار پاسخ زیر ۳۰ ثانیه را نمی‌گیرند. این کار به انتشار سایت، هاست یا دامنه نیاز ندارد، اما تماس با API نیازمند اینترنت است.


## صفحهٔ آمادگی انتشار — فاز 08a

در پنل مدیریت، «آمادگی انتشار» وضعیت بکاپ، ایمیل، نرخ ارز، امنیت و تعمیرات را نشان می‌دهد. دسترسی به مجوز سلامت سیستم نیاز دارد. با «بررسی دوباره» فقط وضعیت تازه خوانده می‌شود؛ سایت منتشر نمی‌شود و عملیات بکاپ اجرا نمی‌شود.

بخش آزمون‌های واقعی تا انجام و ثبت شواهد بررسی‌نشده می‌ماند. تنظیم ایمیل به معنی رسیدن ایمیل نیست و موفقیت بررسی‌های خودکار جای تأیید واقعی HTTPS، گوشی و بازیابی خارج از میزبان را نمی‌گیرد. ثبت شواهد آزمون در فاز ۰۸ اضافه شده است؛ نتیجه را فقط پس از اجرای آزمون ثبت کنید. شواهد محیط محلی یا CI جای پذیرش محیط نهایی را نمی‌گیرند.


## تنظیمات سئو و آدرس‌های بازار — فاز 08b

در پنل مدیریت، «تنظیمات سئو» را باز کنید. مدیر باید مجوز ویرایش برند داشته باشد. عنوان و توضیح پیش‌فرض هر سه زبان از همین صفحه قابل ویرایش‌اند؛ عنوان اختصاصی محصول یا دسته اولویت دارد. کد تأیید گوگل فقط مقدار توکن است و نباید HTML باشد.

نشانی اصلی را در قالب `https://shop.example.com` وارد کنید؛ این کار دامنه را متصل یا سایت را آنلاین نمی‌کند. گزینهٔ ایندکس پیش‌فرض خاموش است و تا پایان پذیرش انتشار باید خاموش بماند. در این حالت `/robots.txt` درخواست منع خزش می‌دهد و `/sitemap.xml` خالی است. این فایل‌ها جایگزین کنترل دسترسی نیستند.

نشانی‌های استاندارد عمومی شامل زبان و بازارند، مثلاً `/tr/m/TR` و `/tr/m/TR/p/slug`. کوکی بازار نمی‌تواند معنای چنین آدرسی را تغییر دهد. صفحهٔ محصول، دسته و محتوای منتشرشده در نقشهٔ سایت بازار مربوط می‌آیند؛ صفحات حساب، سفارش و پنل مدیریت هرگز وارد آن نمی‌شوند. مسیرهای قبلی همچنان قابل استفاده‌اند. تغییر این تنظیمات در سوابق تغییرات ثبت می‌شود و بکاپ عادی آن‌ها را هم نگه می‌دارد.


## امکانات تکمیل‌شدهٔ فاز ۸

- علاقه‌مندی‌ها در حساب کاربری و دکمهٔ قلب کالا در دسترس‌اند. مهمان پس از ورود، علاقه‌مندی همین مرورگر را به حساب منتقل می‌کند.
- برای بررسی نظرها، از «محتوا ← بررسی نظرات» استفاده کنید. نظر و عکس تازه تا تأیید مدیر عمومی نیستند. مجوز لازم همان انتشار محتوا است.
- برای اعلان موجودی، مشتری ابتدا ایمیل خود را با ورود تأیید می‌کند. قالب «stock.available» در تنظیمات اعلان قابل ویرایش است. cron موجود ارسال را انجام می‌دهد؛ برای ایمیل آزمایشی از Mailpit استفاده کنید. مبدأ HTTPS سئو و ارائه‌دهندهٔ ایمیل باید برای ارسال واقعی تنظیم شوند.
- در تنظیمات سئو فقط شناسه‌های عمومی GA4/GTM/Meta را وارد کنید. کلیدهای API همچنان در متغیرهای محیطی‌اند. ابزار تحلیل تا پذیرش کاربر فعال نمی‌شود.
- صفحهٔ آمادگی انتشار اکنون ثبت و تاریخچهٔ شواهد دارد. زمان را با منطقهٔ زمانی وارد کنید، مثل `2026-09-15T12:00:00Z`. شناسهٔ کامل کامیت آزموده‌شده باید با `APP_VERSION` محیط مقصد منطبق باشد. مدرک محلی، تاریخ آینده یا مدرک قدیمی‌تر از ۳۰روز پذیرش واقعی را تأیید نمی‌کند.
- برای مهاجرت، روند موجودِ safety backup و `prisma migrate deploy` را ادامه دهید؛ نیازی به reset دیتابیس نیست. بکاپ دستی، دانلود فایل و بارگذاری برای بازیابی در «سیستم ← پشتیبان‌ها» موجود است.


## دریافت طراحی چهارگروهی جدید

پس از دریافت نسخهٔ ادغام‌شده، سرویس برنامه را با سورس جدید بسازید و migration معمول پروژه را اجرا کنید. مهاجرت `20260919090000_media_presentation` فقط تنظیم قاب عکس را اضافه می‌کند؛ دیتابیس را پاک یا reset نکنید.

برای ارتقای صفحهٔ نمونهٔ قبلی، در محیط برنامه با همان تنظیمات دیتابیس و رسانه اجرا کنید:

```sh
pnpm exec tsx scripts/upgrade-demo-storefront.ts
```

این فرمان فقط محتوای نمونهٔ شناخته‌شده و دست‌نخورده را ارتقا می‌دهد. اگر صفحه را قبلاً شخصی‌سازی کرده‌اید، در **محتوا ← صفحهٔ اصلی** چیدمان بخش آغازین را «چهار گروه با قاب‌های لایه‌دار» انتخاب و ذخیره کنید. تصاویر و ترتیب چهار گروه از دسته‌های اصلی می‌آیند. برای تنظیم برش عکس، **رسانه ← جزئیات تصویر ← قاب‌بندی تصویر** را باز کنید؛ نوع نمایش و دو لغزنده را تنظیم کرده و ذخیره کنید. نمای کامل محصول همیشه عکس بدون برش را نشان می‌دهد.

### اصلاح شباهت بنر به طرح لاویبل

این اصلاح از همان شاخهٔ به‌روز `origin/main` دریافت می‌شود. پس از دریافت کد، کانتینر فعلی برنامه را دوباره راه‌اندازی کنید تا فونت همراه پروژه نصب شود. سپس در همان کانتینر دستور `pnpm exec tsx scripts/upgrade-demo-storefront.ts` را اجرا کنید. این دستور تیتر نسخهٔ نمایشی دست‌نخورده را به «استایل / برای / همه» ارتقا می‌دهد؛ متن‌های ویرایش‌شدهٔ فروشنده حفظ می‌شوند. برای تغییر دستی، در مدیریت صفحهٔ اصلی، چیدمان فضایی را انتخاب و تیتر را در سه خط کوتاه وارد کنید. تصویر انتخابی همان عکس اصلی کمپین خواهد بود. نیازی به ساخت پروژهٔ Docker تازه یا حذف داده‌ها نیست.
